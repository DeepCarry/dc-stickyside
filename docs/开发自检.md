# 便签墙 · macOS 应用

一个本地优先的便签墙。按 `⌥ Space` 随手记一条，`⇧ ⌘ Space` 打开整面墙（两个都能改）。

## 跑起来

```bash
./build.sh          # 出 release 版并打包
open 便签墙.app
```

首次启动会在 `~/Library/Application Support/NoteWall/` 写入 2 条示例便签，直接删掉即可。

## 自检 / 调试

一条命令跑完所有检查：

```bash
./tools/test.sh        # 逻辑自检 + 快捷键占用 + 刘海几何
```

单项：

```bash
swift build --disable-sandbox
./.build/debug/NoteWall --selftest                 # 清单解析、时间格式、存档往返
./.build/debug/NoteWall --locktest                 # 锁定/加密：往返、篡改、拒解锁、图片密文、旧存档迁移
./.build/debug/NoteWall --hotkeys                  # 检查 ⌥Space / ⌘⇧Space 是否被占用
./.build/debug/NoteWall --notchtest out.png        # 刘海几何：入口是否被物理刘海遮挡
./.build/debug/NoteWall --capturetest              # 弹出捕获面板 5 秒（外部截屏取证）+ 滚动条样式断言
./.build/debug/NoteWall --snapshot wall shots/wall.png 1440x920
./.build/debug/NoteWall --snapshot edgefan shots/edge-fan.png 500x760     # 边缘条扇开态
./.build/debug/NoteWall --snapshot edgepull shots/edge-pull.png 500x760   # 边缘条抽出态
./.build/debug/NoteWall --edgetest                  # 边缘条三态上屏 + 几何断言 + 自动截图（不注入系统事件）
./.build/debug/NoteWall --imetest                   # ★ 输入法组合态：拼音不被删、占位显隐、binding 双向同步（18 条）
./.build/debug/NoteWall --walltest [dark]           # ★ 真实主窗口：占位可见、组合输入、⌘↩ 存便签、深色外观
./.build/debug/NoteWall --gridtest                  # ★ 列数：各档窗口宽度 + 真实 Layout 落点 + 3 张主窗口截图
./.build/debug/NoteWall --hovertest                 # ★ 手型光标：真移光标，断言按钮变手型 / 输入框不变 / 空白恢复箭头
./.build/debug/NoteWall --handtest                  # ★ 手型判定状态机：进入即变 / 离开去抖 / 手不动不切（15 条）
./.build/debug/NoteWall --edgeclicktest             # ★ 点纸签时光标稳不稳：真实窗口 + 真机动画，采 32 帧（6 条）
./.build/debug/NoteWall --clickfliptest             # ★ 真光标被 AppKit 洗回箭头后能否在同一事件补回（10 条）
./.build/debug/NoteWall --cursortest                # 正文与占位像素对齐（输出 shots/cursor.png）
./.build/debug/NoteWall --placeholdertest           # 原生占位与 SwiftUI Text 叠合（输出 shots/placeholder-align.png）
./.build/debug/NoteWall --settingstest [dark]       # 设置页真窗口截图
./.build/debug/NoteWall --imagetest                 # 图片粘贴/落盘/读回链路
```

`--snapshot` 走 `ImageRenderer` 离屏渲出**真实视图**，用于在没有屏幕录制权限的环境里检查版式。
AppKit 支撑的控件（`TextEditor` / `TextField` / `Toggle` / `Menu`）在离屏渲染里会画成禁止符，
所以 `RenderFlags.snapshot == true` 时会换成等价的纯 SwiftUI 视图，这只影响截图，不影响运行。

## 应用图标

图标是**代码画的**，没有二进制设计稿：`tools/icongen.swift` 用 SwiftUI 矢量描述构图，
`tools/make-icon.sh` 按 16/32/64/128/256/512/1024 逐档重新栅格化（不是缩放），再 `iconutil` 打包。

```bash
./tools/make-icon.sh     # → Resources/AppIcon.icns
```

`build.sh` 发现 `Resources/AppIcon.icns` 不存在时会自动调用它；改完构图想重出，
删掉 `Resources/AppIcon.icns` 再打包即可。

设计约定：

| 项 | 值 |
|---|---|
| 画布 | 1024×1024，圆角矩形 824×824 居中，圆角 185（macOS Big Sur 起的规范） |
| 底板 | 近黑 `#2E2B33 → #0A090C` 竖向渐变 + 顶部环境光 + 1px 内高光 |
| 主体 | 三张扇形叠放的便签：薄荷 / 淡紫 / 米黄（取自 App 内 `Paper` 色，深色底上不刺眼） |
| 识别点 | 正面便签左上角**勾选框**（产品签名功能）、右下角**卷边**（打破整块黄色，小尺寸也有型） |
| 小尺寸 | 16px 仍能读出「一张带折角的便签」，不做单独简化稿，避免各档观感不一致 |
| 内容占位 | 宽 85.5%、高 77.9%（`IconGeom` 常量）；上留白 17%、下留白 5%、左右各 7% |
| 主体占比 | 正面便签 680/1024 ≈ 66% 宽；侧签 505，只在上角与两侧各露一条 |

预览图：`shots/icon-preview.png`。

### 留白：不能只看「内容外框」

v0.9.8 之前主体便签只有 468/1024（46% 宽），两张侧签向两侧扇开、把内容外框撑到 84%——
**量 bbox 是够满的，看上去却「里面东西小」**，用户一眼就看出来比 QQ 那类图标空。

所以判断留白要看**主体**占多大，不是看内容并集：

| 版本 | 内容外框 | 主体便签 | 观感 |
|---|---|---|---|
| 0.9.7 | 84% × 70% | 46% | 空，四周一圈黑边 |
| 0.9.8 | 85.5% × 77.9% | 66% | 与同类图标一致，上留白略多于下 |

改法：主体 468 → 680，侧签 322 → 505 且横向让位 138 → 148（只是略宽，不再靠扇开撑轮廓），
整组下移让重心落在下 3/4。**没有用 `scaleEffect` 等比放大整组**——那样侧签会一起顶到圆角被切掉，
而且主体占比不变，等于没解决。

## 菜单栏图标

菜单栏图标是 **App 图标的实心版**（v0.9.13）：跟系统里其它菜单栏图标同一套关系——
**形状是填满的，细节（勾选框、四行字、纸间缝隙）是挖空的**。

早先做反了：形状是透明轮廓、线条是白的，在菜单栏里像一层薄线框，跟旁边那些实心图标格格不入。

| 项 | App 图标（1024） | 菜单栏（18pt） |
|---|---|---|
| 前纸 | 680 / −3.5° / 下移 100 | 11.95pt / +3.5° |
| 左纸 | 505 / −12° / x−148 / 上提 50 | 10.55pt / +9° / x−2.3pt / 上提 2.6pt |
| 右纸 | 505 / +11° / x+148 / 上提 38 | 10.55pt / −9° / x+2.3pt / 上提 2.6pt |
| 纸间缝 | — | 0.85pt（`destinationOut` 沿轮廓擦出来的透明缝） |
| 纸面内容 | 勾选框 0.125w、四条线 0.46/0.44/0.34/0.26w | 同比例，内边距 0.135w |

四个约束（都是量出来的，不是估的）：

1. **后纸要放大到 600**。照搬 505 时，18pt 上后纸露出的部分只剩一道发丝（1px），
   被透明缝一切就散成噪点；放大到 600 后两侧才有 2pt 左右的实心纸边。
2. **实心 + 挖空靠 `destinationOut`**：画左纸 → 沿右纸轮廓擦缝 → 画右纸 → 沿前纸轮廓擦缝 →
   画前纸 → 把纸面内容整个擦掉。擦的宽度是缝宽的两倍（一半在里一半在外），留下的才是缝。
3. **1x 单独加粗**：18px 只有 18 颗像素，横线不加粗会被抗锯齿抹平；
   但缝加太粗又会把两侧的纸吃光，所以 1x 用 `gapHint 1.2 / contentHint 1.5`，2x/3x 用 1。
4. **四周留白 ≥ 1pt**：整组摊开是 16×15pt，正好卡在 18pt 画布里。

```bash
./.build/debug/NoteWall --menubaricon --iconmap   # 18 项断言 + 打印 1x/2x 点阵
./.build/debug/NoteWall --mbgeom                  # 叠放几何对照（调参用）
```

18pt 的物理上限：36px（2x）下三张纸、勾选框、四条线都分得开；18px（1x）只剩「一张带字的便签」，
后两张退化成两个纸角——这是像素数量决定的，不是画法问题。

### 右键菜单

```
新建便签
打开便签墙
─────────
设置…        ⌘,
─────────
退出         ⌘Q
```

分组照 macOS 惯例：动作 / 设置 / 退出。设置单独一组、退出压最下，跟系统 App 的读法一致。

- **「设置…」不在菜单栏里另造一套 UI**：它把墙窗口带回前台，再让墙窗口弹自己的设置 sheet
  （`WallView` 里的 `SettingsSheet`）。菜单栏和无刘海降级入口共用同一份设置。
- 墙窗口可能已经被关掉（App 还常驻菜单栏）。这时 `bringWallToFront` 重建窗口，
  而新窗口的 `onAppear` 比通知晚，所以真正的开关是 `AppContext.pendingOpenSettings` 这个旗子，
  通知只是「窗口已开着」时的快路。
- **action 名别叫 `openSettings`**：AppKit 会按名字给它自动配一个齿轮图标，菜单里就它一个带图标，
  很跳。改成 `openPreferences` 就干净了（实测）。
- 菜单内容抽成了 `AppDelegate.makeStatusMenu(target:)`，`--menutest` 才能不启动界面就断言
  「每项都绑了 target / 都有 action / 都是 enabled」——这类菜单最常见的失败是看着正常、点下去没反应。

```bash
./.build/debug/NoteWall --menutest              # 条目、顺序、快捷键、target
./.build/debug/NoteWall --settingsfrommenu      # 真实窗口：点「设置…」后 sheet 挂上了
./.build/debug/NoteWall --menupreview           # 把菜单弹到屏幕上截一张（看图确认排版）
```

## 纸色切换的形状

换纸色的六个控件是**圆角方形**，不是圆形色点。

便签纸是方的，方形色块能被直接读成「换一张纸」；圆形只会读成「一个色点」，
像调色盘上排开的按钮，跟「纸」没有关系。

| 项 | 主窗口 | 捕获面板 / 详情页 | 说明 |
|---|---|---|---|
| 色块 | 17×17 | 15×15 | 够小不抢文字，又足以看出是「一张纸」 |
| 圆角 | 3.4 | 3.0 | 约边长的 20%。再圆就像 App 图标，再方就是硬色块 |
| 间距 | 7 | 7 | 方块视觉比圆点重，间距不能比旧版更小 |
| 选中 | 外环 1.3pt + `scale 1.045` + 投影加重 | 同 | 像从一叠里抽出一张 |
| 命中区 | 24×24 | 22×22 | 比色块大，点击不费劲 |

纸面还叠了一层极轻的上亮下暗（白 10% → 黑 4%），16pt 上也有厚度感，不会平得像色标；
描边只留 ink 9%——白纸块放在米黄纸面上仍然看得出边界，但不会被描成「按钮」。

实现是 `Theme.swift` 里的 `PaperSwatch`，主窗口输入区 / 捕获面板 / 详情页三处共用。

## 外观：浅色 / 深色 / 跟随系统

设置页第一组就能切，切换立刻生效，不需要重启，也不会丢掉正在编辑的草稿。

之前整窗只有一种底色（`#0A0A0C`），卡片飘在近黑上，看起来是一团黑。现在每一层都有明确明度：

| 层 | 深色 | 浅色 | 用途 |
|---|---|---|---|
| 画布 | `#212125` | `#FFFFFF` | 便签网格底 |
| 顶栏 | `#2E2E33` | `#EFEEE9` | 标题 / 墙 tab / 输入区 / 筛选条 |
| 浮层 | `#35353B` | `#FFFFFF` | 捕获面板、弹层 |
| 控件 | `#3E3E45` | `#FFFFFF` | 抬起的按钮、输入框 |

便签墙没有系统标题栏、也没有侧栏，界面原本是一整片同色，看不出「工具在哪、内容在哪」。
顶栏单独给一块底色 + 一条 1pt 分隔线，就有了分区。

方向在深/浅下相反，因为「凸起」的视觉线索本身相反：

- 深色：顶栏比画布**亮**（33 → 46，差 13 级），像一块被灯照亮的工具栏；
- 浅色：顶栏比画布**暗**（255 → 239），米灰顶栏 / 纯白便签区——白纸留给便签，
  灰留给工具，跟 macOS 的浅色窗口一致。

实现要点：

- 所有 token 写成一对色值（`Color.dyn(light:dark:lightAlpha:darkAlpha:)`），交给
  `NSColor(name:dynamicProvider:)` 在绘制时解析。**不要**写成 `Color.white.opacity(0.06)`——
  深色下「提亮」、浅色下必须「压暗」，同一个白透明度在两套主题里含义相反。
- 主窗口的外观由 `preferredColorScheme` 驱动（`store.appearance`）。**只设 `NSApp.appearance`
  不会让已经开着的窗口换色**——实测点了没反应，见下面第 12 条。
- 捕获面板是独立 `NSPanel`，不在主窗口的视图树里，每次 `show()` 单独下发 `panel.appearance`。
- 刘海面板固定黑：它是物理刘海的延伸，系统切浅色也不该变白。
- 浅色下阴影要轻（10–16%），深色下要重（30–40%）；卡片描边同理，浅色用 5.5% 黑、深色用 22% 白。

## 结构

| 文件 | 作用 |
|---|---|
| `Models.swift` | `Note` / `Wall` / `Paper`、清单语法解析、时间显示规则、排序与筛选枚举 |
| `Store.swift` | `AppStore`：加载、防抖原子保存、增删改查、墙管理、筛选与排序、撤销栈、锁定/解锁 |
| `Filters.swift` | 三个筛选维度：纸色（多选）、时间、状态 |
| `Edits.swift` | 撤销步、Toast、拖拽状态与两个 `DropDelegate` |
| `Vault.swift` | AES-GCM 256：主密钥、便签密文、图片原地加密 |
| `Biometrics.swift` | Touch ID / 登录密码验证（`LAContext`），可替换实现供自检 |
| `ImageStore.swift` | 图片落盘（长边 ≤2048、640 缩略图）、粘贴板取图 |
| `Theme.swift` | 设计 token（颜色/字号/圆角/间距）与胶囊按钮、chip 等复用控件 |
| `WallView.swift` | 主窗口：顶栏、墙 tab、输入区、筛选条、瀑布流；`WallContent` 可脱离滚动容器渲染 |
| `NoteCard.swift` | 便签卡片、正文分块（文字段 / 清单段）、缩略图缓存 |
| `Masonry.swift` | `Layout` 实现的瀑布流，列宽自适应 300–420pt |
| `Sheets.swift` | 便签详情、回收站、设置 |
| `Capture.swift` | 全局捕获面板（`NSPanel`，非激活、居中、⌘↩ 保存、⌘⇧P 钉住、⌘V 粘图） |
| `Notch.swift` | 刘海入口：黑色面板盖住物理刘海，悬停向两侧展开两个入口；刘海边界取自 `auxiliaryTopLeftArea/RightArea`，入口锚在边界外侧 |
| `EdgeDeck.swift` | 屏幕边缘条：细条 / 扇开 / 抽出三态，`NSPanel` 常驻最前；纯几何 `EdgeDeckGeom` 供断言 |
| `HotKey.swift` | 可配置的全局快捷键：组合键模型、按键显示、校验与冲突引导、Carbon 注册与失败回滚 |
| `Snapshot.swift` | 离屏渲染与自检入口 |
| `NoteWallApp.swift` | App 壳、`AppContext`（全局唯一 store）、菜单栏入口 |

## 拖动、菜单与撤销

这一版补齐的三件事都属于「像纸」的手感：随手挪、随手改、随手后悔。

**卡片菜单**：悬停才出现的 `⋯` 只有一个入口，里面是 打开 / 置顶 / 移动到墙 ▸ / 锁定 / 复制文字 / 删除。
右键菜单和它共用同一份定义（`NoteCard.actions`），不会出现「右键少了两项」。
指针停在 `⋯` 上时卡片不响应单击，否则点菜单会连带打开详情页。

**拖拽**：卡片既是拖拽源也是落点。落在卡片**上半**插到它前面、**下半**插到它后面，
判断依据是卡片真实高度（`GeometryReader` 上报，不写常量），插入位置画一条 3pt 的金色指示线。
落点在**同墙内**时做重排：只重整这面墙的顺序号（`i * 100`），并把排序切成「手动」——
不然按时间排序时拖动看起来毫无反应。跨墙靠**拖到墙 tab**，因为网格里只显示当前墙，
「拖到看不见的墙」不可能靠卡片落点完成。

**撤销**：自建 30 步栈，不用 `NSUndoManager`——它按 First Responder 找 target，
而焦点几乎总在 `TextEditor` 里，`⌘Z` 会被文本编辑抢走。反过来，焦点在文本框时我们
**主动让位**（`NSApp.keyWindow?.firstResponder is NSTextView` 就 return false），
保证「刚打的字能撤」优先于「撤销删除」。每步都带标题，删除/移墙/重排都会在底部弹一条
带「撤销」按钮的 Toast。清空回收站是不可逆操作，顺手清空历史，不给假的后悔入口。

## 锁定到底锁了什么

`⌘` 语境下「锁定」很容易变成一层遮罩：看起来挡住了，文件里还是明文，随便一个备份、搜索索引、
文本预览都读得到。这一版把它做成了真的：

| 项 | 做法 |
|---|---|
| 正文 | 序列化成 `LockedPayload` → AES-GCM 256 → `v1:<base64>` 存进 `lockPayload`；`text` 立刻清空 |
| AAD | 每张便签把 **note id 当附加认证数据**，把 A 的密文塞给 B 直接认证失败 |
| 图片 | 主图与缩略图**原地换成密文**（`image.isEncrypted = true`），解锁时原地还原 |
| 内存 | 锁定同时逐出 `ThumbCache` 里的明文缩略图，否则「锁上了但内存里还留着图」 |
| 密钥 | `~/Library/Application Support/NoteWall/vault.key`，32 字节随机数，权限 `0600`，排除出 Time Machine |
| 解锁 | `LAContext`，有 Touch ID 用生物识别，没有退到登录密码；**验证不过就保持密文** |
| 退出 | 本次会话解过锁的便签，`applicationWillTerminate` 里重新封上，明文不留过夜 |
| 存档 | 只写密钥指纹 `keyID`（sha256 前 6 字节），不写密钥本身 |

**为什么不放钥匙串。** PRD 原话是「密钥存钥匙串」，实测后改成独立文件：本机是 ad-hoc 签名，
每次重新构建 cdhash 都会变，钥匙串条目的 ACL 只认签名身份，于是**每次启动都弹一次系统授权框**
（开发过程中真的弹了，要输登录密码）。把授权框挂在每一次启动上，用户三天就会把 App 卸了。
独立文件的强度确实低于 Secure Enclave，但它保住了「不在存档里、不进备份、不跟存档一起被拷走」这一层，
而真正的门禁是 Touch ID 那道验证。要升级成硬件绑定，只改 `Vault.loadOrCreateKey()` 一个函数，上层不动。

**边界也要说清楚。** 这道锁防的是「别人翻我的文件 / 备份 / 存档预览」，不是「本机上以我的身份运行的恶意程序」——
后者能读这个文件，就能读密钥。任何不依赖 Secure Enclave 的本地加密都过不了这一关，别把它当 FileVault。

**失败时的样子。**
- 验证被拒 → 内容保持密文，卡片仍显示「已锁定」；
- 主密钥被换（指纹不一致）→ 存档里 `keyID` 对不上就置 `keyStale`，卡片与设置页都写「无法解密」，
  而不是给你一个空编辑框让你以为内容没了；
- 解锁方式不可用（没有 Touch ID 也没设登录密码）→ **禁止锁定**。锁进去打不开不叫安全，叫数据丢失。
- 被系统强杀 / 崩溃时 `applicationWillTerminate` 不执行，明文会留到下次解锁；正常退出不会。


## 刘海入口的几何约束

物理刘海是硬件遮挡，宽度随机型变化（本机 185pt × 32pt），**不能用常量、也不能按面板中心对称排图标**。
正确做法是从系统读边界：

```swift
NSScreen.auxiliaryTopLeftArea   // 刘海左侧可用菜单栏区域
NSScreen.auxiliaryTopRightArea  // 右侧
// 刘海宽度 = right.minX - left.maxX
```

布局规则（`NotchGeometry`）：

| 量 | 规则 | 本机实测 |
|---|---|---|
| 收起宽度 | **严格等于刘海宽**（不画任何像素） | 185 |
| 展开宽度 | 刘海宽 + 2×(净距 12 + 图标 68 + 边距 10) | 365 |
| 图标到刘海边缘 | ≥ 12pt | 12 / 12 |

收起态必须与刘海**同宽且零绘制**：物理刘海本身就是黑的，我们再补黑只会把多出来的部分
画到菜单栏上，圆角刘海就变成一条直角黑条。同宽的副作用是好事——不会盖住刘海两侧的菜单栏项目。

`--notchtest` 三条断言：

1. 左右图标矩形与刘海矩形无交集（净距 < 8pt 判失败）；
2. 收起面板宽度 == 刘海宽度；
3. 收起态离屏渲染后**可见像素数为 0**（`NotchPixel.countVisible`，alpha > 2 即算画了东西）。

### 点击态（阶段③）· 等比放大

悬停出的两翼只是「入口」，点开后要变成一块面板。比例规则：**宽高比锁死物理刘海**
（本机 185 ÷ 32 ≈ 5.78 : 1），圆角按同一比例放大 —— 这样读起来是「刘海变大了」，
而不是「刘海下面鼓了个包」。

| 倍数 | 尺寸 | 占屏宽 | 菜单栏下方可用高度 |
|---|---|---|---|
| 1.0× | 185 × 32 | 12% | 0（基准，就是硬件） |
| 1.5× | 278 × 48 | 18% | 16 |
| 2.0× | 370 × 64 | 24% | 32 |
| 2.5× | 463 × 80 | 31% | 48 |

```bash
./.build/release/NoteWall --notchratio shots/notch-ratio.png   # 出对照图
```

图按**真实屏宽**作画，旁边画了菜单栏项目占位块 —— 否则面板会显得夸张地大，看不出它吃掉多少菜单栏。

代价要说清楚：等比形态是**一条横带**，不是一块容器。2.0× 时菜单栏下方只有 32pt，
只放得下一行内容（快速输入 + 两个动作）。PRD 阶段③原本计划的「最近 3 条缩略」放不进去；
真要放，就得放弃固定比例，改成宽度 ≥1.5×、高度自由的连续面板（NotchNook 式）。
两种形态不能混用——混用就是「略宽一点」那个死亡区间。

## 屏幕边缘：三种形态，一条直线

屏幕边缘常驻一条 12pt 的细边，鼠标移过去扇开成纸签，点一张整张便签从边缘抽出来直接编辑。
一条铁律贯穿三态：**贴屏幕的那一侧永远是直线、零缝隙**，所有层次只发生在朝屏幕内侧的那条边。

| 态 | 形态 | 关键规格 |
|---|---|---|
| ① 静止 | 半透明胶囊，每条便签一个纸色点 | 宽 12pt、贴边侧切平（只有内侧有圆角），高度只够装色点 |
| ② 悬停 | 纸色纸签，中文竖排标题，相邻交替倾斜；底部常驻两颗圆钮 | 32×116，步进 68（每张完整露出 4 字），级联 45ms，离开 320ms 才收拢 |
| ③ 点击 | 完整便签摊开 + **签列仍在** + 两颗圆钮 | 面板 330×248–420（随内容），面板纵向对齐它原来那张签 |

**为什么倾斜而不是整张飘起来。** 倾斜的旋转轴钉在贴边那条线上（`rotationEffect` 的 `anchor` 取
`.trailing` / `.leading`），所以转的是内缘，贴边侧不动。再加上贴边元素向屏幕外多伸 4pt 被屏幕裁掉：
3° 旋转会让四角各内缩约 2.9pt，不留这点余量某些角度下仍会露出发丝缝。

**抽出态不是「只剩一张纸」。** 第一版抽出一张就把签列整个收掉，读起来像「点一下，其他便签消失了」，
用户会以为点坏了。现在面板在左、签列照旧贴在右边缘，被抽出的那张扶正（0°）并打一道墨色标记——
「这张纸是从这一列里拿出来的」在几何上说得出因果，而不是凭空出现一张大卡片。
面板的纵向位置跟着它原来那张签走（第 N 张就下移 N 个步进），所以永远不会跟自己的来源错位。

**底部两颗圆钮**（`macwindow` 打开便签墙 / `plus` 新建）挂在签列末尾，**扇开态就在**——
它们是这一列的常驻出口，不该等到「点开一张便签」才出现（那是查看，不是菜单）。
新建走的是全局捕获面板，和 `⌥Space` 同一条路，不另造一套流程。
换一张便签不需要收起再展开：直接点签列里的另一张，旧草稿先落盘再切。

**窗口四周必须留衬边，且要按阴影的两倍留。** 这是「半透明边框」的唯一解，本项目踩过两次（坑 3、坑 19）：
SwiftUI 的 `shadow` 画在视图外，窗口紧贴内容时会被窗口边界硬切成一条**直边灰带**。
关键数字：**CoreGraphics 的 `shadowBlurRadius` 是名义模糊半径，可见尾迹拖到约 2×radius**——
按 `radius + offset` 留衬边，边界处仍残留一层淡影，照样被切。
所以 `innerPad ≥ 2×radius + |offset| + 2`：细条 0 / 扇开 18（6×2+3+3）/ 抽出 26（10×2+4+2），
而且**上下也要留**（第一张签和最后一张、面板顶底都会投影）。贴边侧仍然只多伸 4pt，
`EdgeDeckGeom.contentEdge` 就是用来断言「衬边只长在内侧、贴边侧还是一条直线」的。

**投影只投一次。** 每张签各投一次时，相邻签的阴影会在衬边上叠成 5 层 30% 黑，连成一条均匀灰带
（看着又像边框）。改成整个 `ZStack` 离屏渲染后统一投影，重叠的签被当成一个轮廓，只落一层。

**两种模式**（互斥、可切换，不混用）：最近编辑自动取前 N 张（默认 8，可调 3–12），或手动钉住——
从卡片「⋯」菜单逐张钉，数组顺序就是显示顺序。混用（钉住优先 + 最近补足）会让用户搞不懂
「为什么我刚写的那张没在边上」。

**安全规则比主窗口更严**：锁定与回收站的便签在 `edgeNotes` 数据层就排除——边缘是「路过就能看到」的界面，
不能成为锁定内容的泄漏口。抽出面板写回前再校验一次锁定态，防止「打开时没锁、写回时已锁」把明文塞进密文便签。
锁定但被钉住的便签只保留 id，解锁后自动回到边缘。

**不抢焦点**：面板是 `nonactivatingPanel`，点开后成为 key 借走键盘，但 App 不激活——
你在别的应用里打字，鼠标移到边缘记一笔，前台应用一直在那。只有抽出态才允许 `canBecomeKey`。

**多屏**：跟着便签墙窗口所在屏，纵向居中于 `visibleFrame`；窗口被拖到别的屏、屏幕参数变化都会重新定位，拔掉外接屏不会落在虚空坐标上。
跟窗口而不是跟鼠标：鼠标随手一划就换屏，条会跟着乱跳；用户对「我的窗口在哪块屏」才有稳定预期。

**首次提示**：默认开启，第一次启动弹一条 Toast 指路——12pt 细条存在感极低，不说一声很多人永远发现不了。

## 设置页：可点的控件要长得像控件

设置页是用户唯一会「逐条读」的界面，排版上的小毛病在这里最刺眼。三条硬规则：

**① 内容必须撑满并居中。** 窗口 600，左右各留 28，中间 544——用
`.frame(maxWidth: 544)` 先限宽、再 `.frame(maxWidth: .infinity, alignment: .center)` 居中。
只写 `maxWidth: .infinity` 会让每张卡片按自己内容的长度缩，视觉上是「左边齐、右边参差」。
另外常驻滚动条会在右侧硬吃 15pt，看起来就像「整体偏左」——统一压成 overlay（`ScrollChrome`），
静止时不占位、滚动时才浮出来。

**② 能点的东西必须有可点的长相。** 开关是系统 switch，按钮有底色和描边，
下拉用 `Picker(.menu)`——**不要用 `Menu` + `borderlessButton`**：那套样式会把自定义 label
简化成一行纯文字，还会在文字**左边**补一个箭头，结果比原来的裸文字更不像控件（这条踩过，见坑 20）。
只读信息（Touch ID / 已锁定 / 密钥文件名）反过来：不给底、不给边，只靠右对齐和颜色区分，
免得它和下拉抢同一套视觉语言。

**③ 分组要有边界和节奏。** 每组是「小标题 + 圆角卡片」，卡片有一圈 0.5pt 描边，
行与行之间 0.5pt 分隔线并左缩进 14（最后一行不画，否则卡片底下会多一条半截线）。
组间距 26、组标题到卡片 8、行内上下 11——这三档固定，不再逐个微调。

步进器同理：系统 `Stepper` 是两根 8pt 的上下箭头，一行设置里几乎看不见，
也说不清「现在是多少」；换成 `[−] 8 张 [＋]` 一体胶囊，和下拉、开关同一水平线。

## 图片：三条入口，一套存储

便签的图片不是「附件」，是和正文平级的第二种内容——所以 `Note` 允许
`text` 为空、`image` 非空，纯图片便签是合法的一张纸。

**三条入口，走的都是 `ImageStore`：**

| 入口 | 快捷键 | 落点 |
|---|---|---|
| 主界面输入区 | ⌘V 或把图拖到纸上 | 先变成草稿附件，和文字一起提交 |
| 全局捕获面板 | ⌘V 或拖入 | 当场预览，保存时落盘 |
| 详情页 | ⌘V | 直接替换当前便签的图（旧文件一并删除） |

**剪贴板有四种形态，必须全认：**① 截图/浏览器复制（tiff、png 位图）；② `NSImage` 对象；
③ **访达里复制的图片文件**（只有 fileURL，没有位图数据）；④ 纯文本（不该接管）。
漏掉第 ③ 种是最常见的坑：⌘V 会把 `/Users/...` 路径当普通文本插进输入框，
用户看到的就是「便签不支持图片」。

**必须在键盘监听里拦下 ⌘V。** `TextEditor` 自己会处理粘贴，图片在它眼里就是一段文本。
`KeyMonitor` 的本地监听先于 responder chain，`ComposerPaste.image()` 判断该不该接管，
接管就 `return true` 吞掉事件。

**存储**：长边压到 2048、另存 640 的缩略图（列表只读缩略图，详情页才读原图）。
彻底删除便签、或替换图片时，旧文件立刻从磁盘删掉；锁定便签时连内存里的缩略图缓存一起清。

## 快捷键：能改、会拦、会回滚

`⌥ Space` 是 Raycast / Alfred 和一堆输入法增强工具的默认键。一个便签 App 占着它，
在装了这些工具的机器上表现就是「按了没反应」，而且用户无从知道原因。所以两个全局键都做成可录制的，
并且把「为什么这个组合不能用」写清楚。

**录入**：点设置里的组合键 → 变成「按下新的组合键」→ 敲下即生效，`Esc` 取消。
按住修饰键时实时显示「⌥ …」——「按下 ⌥ 之后还要按什么」这件事没有别的反馈渠道。

**两层规则**，分开是因为性质不同：

| 层 | 例子 | 行为 |
|---|---|---|
| 硬性（`problem`） | 裸字母、只有 ⇧ | 直接拒绝，并说明原因 |
| 软性（`advisory`） | ⌥ Space（启动器）、⌘ Space（聚焦搜索）、⌃ Space（切换输入法）、⌘ ⇧ 3/4/5/6（截屏）、⌘ + 单个字母 | 允许，但在行下写清代价 |

⌘ + 单个字母那条值得单说：全局快捷键是从**所有 App** 手里把这组键接过来，设成 ⌘C 之后
每个应用都复制不了。这类「能用但会毁掉别处」的组合不该被静默接受。

**占用检测**：Carbon 的 `RegisterEventHotKey` 在组合已被占用时返回 `eventHotKeyExistsErr`（-9878）；
本进程重复注册同样会失败，所以「先试注册、再注销」就是一次可靠的探测。

**回滚**：改键走 `apply(config, strict: true)`——先全部注销，再逐个注册；任何一个失败就把整组退回改动前的配置。
不这么做会出现「新建便签换成 ⌘K 成功、打开墙失败」的半吊子状态：用户看到一半能用一半不能，
排查成本远高于直接拒绝。失败时设置页留在录键态，方便立刻重试。

**启动时**用 `strict: false`：能注册几个算几个，失败的位弹一条 Toast 明说「被其他应用占用，可在设置里更换」。
这是用户唯一能感知「快捷键没反应」的地方，只写 NSLog 等于没说。

**显示顺序**是 ⌃ ⌥ ⇧ ⌘，跟系统菜单一致（`⇧⌘N` 而不是 `⌘⇧N`）。旧版硬编码的 `⌘ ⇧ Space` 其实不合 Apple 的规范，
这次一并改掉了。

## 三十二个踩过的坑

1. **本机只有 Command Line Tools**，没有 `SwiftDataMacros` / `SwiftUIMacros` 插件，
   因此不能用 `@Model`、`@State`、`@Binding`、`@Environment`。存储改为 Codable +
   经典属性包装器；`Package.swift` 仍可用 Xcode 直接打开，装好 Xcode 后这些限制自动消失。
2. **构造脚本要幂等**：这个环境里同一条命令偶尔会被执行两次，写文件的脚本必须先判断再替换，
   否则会写出重复的 CSS 规则 / 重复的 Swift 声明（`invalid redeclaration`）。
3. **透明无边框窗口的阴影，两件事要同时做对**：
   ① `hasShadow = true` 时系统按窗口矩形（直角）画阴影，会压在圆角卡片外面 → 关掉，改由 SwiftUI 自绘；
   ② 自绘阴影的扩散半径必须 **小于** 卡片外圈的透明 padding，否则阴影会在窗口边缘被硬切，
   表现就是「卡片外面多了一圈半透明边框 + 角落一块深色」。当前：`shadow radius 12 / y 5`，
   `padding 24`。阴影参数和 padding 是一对，改一个必须一起改。
4. **占位文案必须与 TextEditor 文字起点对齐**：NSTextView 自带 `textContainerInset.width
   + lineFragmentPadding`（约 9pt），裸排的占位文字不做同样内缩，光标就会压在占位字上。
   内缩量从运行时真实的 NSTextView 读取（`EditorMetrics`），不要硬编码猜。
5. **硬件遮挡区域不要「补一块」**：刘海是物理黑，面板只要比它宽出一点点，多出的部分就是
   压在菜单栏上的黑像素，原生圆角会被拉成直角黑条。覆盖类面板的默认态应当零绘制。
6. **系统「总是显示滚动条」会毁掉深色卡片**：`TextEditor` 右侧会出现一根直角深色竖条。
   `.scrollIndicators(.hidden)` 对 `TextEditor` 无效；`NSScroller.preferredScrollerStyle`
   是只读的。可行做法：遍历窗口层级把每个 `NSScrollView` 的 `scrollerStyle` 设为 `.overlay`
   （`ScrollChrome`，在窗口成为 key 后延迟 0.12s 执行，等 TextEditor 把滚动视图建出来）。
7. **拟物化控件的形状要跟真实物体一致**：用圆形色点换「纸色」说不通——现实里没有圆形便签，
   圆形会被读成「色标/按钮」。改成圆角方形后同一个交互立刻自解释。换形状时注意两点：
   ① 方块的视觉重量大于同尺寸圆形，间距要相应加大（7pt 起）；
   ② 描边要收（ink 9%），否则一圈深色内描边会把「纸片」变回「按钮」。
8. **`HStack(alignment: .top)` 里的矮元素必须自己撑高**：顶栏的「N 张便签」只有 11.5pt 高，
   而搜索框 30pt，两者按顶部对齐 → 实测中心差 8.2pt，看着就是「没对齐」。
   给矮的那个加 `.frame(height: 30)` 让它参与同一套居中，改完偏差 0.2pt（像素级）。
9. **快捷键通道装好了不等于快捷键能用**：`KeyMonitor` 只是个转发器，`install()` 之后没人
   `add` handler，`⌘↩` 就是彻底无效的（曾经如此）。凡是全局/局部按键，必须有一条断言或
   一次真实按键验证，不能只看代码里「有这段逻辑」。
10. **钥匙串在 ad-hoc 签名下不可用**：钥匙串条目的 ACL 绑定签名身份，而 ad-hoc 签名的身份就是
    cdhash——代码一改就变。把主密钥写进钥匙串的结果是「每次构建后启动都弹一次系统授权框，
    还要你输登录密码」。密钥改放 `0600` 独立文件（同一目录、排除备份），弹窗消失。
    凡是「系统托管的密钥/凭证」，先确认签名方式，再决定要不要用。
11. **监听挂了不等于回调会来**：`ScrollChrome` 只监听 `NSWindow.didBecomeKeyNotification`，
    而它在 `applicationDidFinishLaunching` 里注册时，窗口**早就是 key 了**，通知不会补发。
    结果这段代码一次都没执行过，TextEditor 的滚动条一直没被处理（浅色主题下是一条刺眼的竖白条）。
    凡是要「扫一遍现有窗口 + 以后跟着变」的逻辑，注册时就得先对现存对象处理一次。
12. **改 `NSApp.appearance` 不一定会重绘 SwiftUI**：已存在的窗口不会因此重新解析动态色，
    表现是「在设置里点了浅色，窗口纹丝不动」。可靠的路径是让 SwiftUI 自己管：
    `preferredColorScheme` 随 store 变化 → 整棵子树重算 → 动态色重新解析。
    `NSApp.appearance` 只负责 AppKit 自己画的东西（菜单、`NSAlert`、交通灯）。

13. **离屏渲染画不了 `.onDrop` / `.contextMenu`**：`ImageRenderer` 会把它们画成
    「黄色底板 + 红色禁止符」，贴在内容底下。第一次遇到时以为是卡片多了条黄边，
    查了半天样式，其实是截图工具的限制。凡是给截图路径用的视图，这类修饰符要按
    `RenderFlags.snapshot` 摘掉；否则截图没法用来做像素核对。
14. **`⌘Z` 不能无条件拦截**：本地键盘监听会先于文本框收到事件，直接吃掉就等于
    「在输入框里撤销不了刚打的字」。判据是 `NSApp.keyWindow?.firstResponder is NSTextView`，
    命中就放行。同理，`⌘↩` 这类自定义快捷键要在有弹层时整组让位。

15. **F 键的虚拟键码不是递增的**：`kVK_F1` = 122、`kVK_F12` = 111。写 `kVK_F1...kVK_F12`
    这种区间会在构造时直接崩：`Fatal error: Range requires lowerBound <= upperBound`，
    而且因为它发生在应用启动早期的静态初始化里，栈上看不出和 F 键有关。F1–F19 一律用显式表映射，
    不要对键码做算术。

16. **`UCKeyTranslate` 在新 SDK 里的参数顺序和 Apple 文档不一致**：文档写的是
    `(…, maxOutputStringLength, outputString, &actualLength, &deadKeyState)`，
    实际导入的是 `(…, &deadKeyState, maxOutputStringLength, &actualLength, &outputString)`。
    按文档传的结果是每个字母都翻出「⌥ + 字母」的变音符（A → ä）——死键状态被写成了 4。
    这类「编得过、跑得动、只是结果全错」的绑定错误，只能靠打印真实输出来核对。
    顺带一条：在 struct 体内写自定义 `init` 会吃掉合成的 memberwise init，
    给 `HotkeyCombo` 加 `init(event:)` 之后所有 `HotkeyCombo(keyCode:carbonModifiers:)` 都编译不过，
    得放进 `extension`。

17. **`ZStack` 不把 `offset` 算进固有高度**：把一叠签用 `.offset(y: idx * step)` 排开时，
    `ZStack` 的高度仍只是一张签（116pt）。结果是整叠签按一张签那么高居中，后面的签直接画到窗口外面。
    必须显式 `.frame(height: stackHeight)` 撑开容器。这类「布局尺寸 ≠ 绘制范围」的错，
    截图看起来像「位置没对齐」，实际是容器根本没长高。

18. **贴边类的旋转，轴必须钉在贴边线上**：`rotationEffect` 默认绕中心转，一张 116pt 高的签转 3°，
    贴边侧上下角各内缩约 3pt，视觉上就是「纸飘起来了、边上有缝」。正确做法两件事一起：
    ① `anchor` 取贴边侧（`.trailing` / `.leading`）；② 元素向屏幕外多伸几 pt 被屏幕裁掉，
    兜住旋转带来的残余偏移。

19. **同一个「透明边框」的错，会以不同面目回来**（第二次，比坑 3 更隐蔽）：
    抽出面板的窗口宽度正好等于内容宽度，看起来「更贴边、更干净」，实际上把两件事一起切坏了——
    ① 面板 `shadow` 全被窗口左边界硬切成一条**直的半透明竖带**；
    ② 内缘那块 17pt 的 `hangingTab` 顶部让出一段透明，和面板圆角拼成一个**直角块**。
    两者叠起来，就是用户说的「卡片旁边套了一圈透明窗框，跟之前那个悬浮窗一个毛病」。

    **第一次修错在「按 radius 留衬边」**：留了 `radius + offset` 仍然有一条淡影，因为
    CoreGraphics 的 blur 尾迹约 **2×radius**，边界处还剩 1–3% 的黑，被窗口一刀切平。
    另外只留了左右、没留上下，面板顶底同理被切。用户第二次截图抓的就是这条。

    根治三件事一起做：① 衬边 `2×radius + offset + 2`，四边（除贴边侧）都留；
    ② 投影从「每张签各投一次」上移到整个 `ZStack` 投一次，避免多层阴影叠加成灰带；
    ③ 把它变成几何层硬约束 `EdgeDeckGeom.bleed(for:)` + `contentEdge()` 断言。
    判断方法：**阴影的实际扩散 ≥ 窗口到内容的距离，就一定有硬切边**（按 2×radius 估，别按 1×）。

20. **`Menu` + `.borderlessButton` 会吃掉你自己的壳**：想给下拉做「胶囊底 + chevron」，
    结果系统把自定义 label 简化成一行字，还在**左边**塞一个箭头（"⌄ 右侧"），
    比原来的裸文字更不像控件，而且这个组合在 macOS 上不会报错、离屏渲染也看不出来——
    只有开真窗口截图才会露馅。要么用 `Picker(.menu)` 拿系统标准外观，
    要么用 `NSMenu.popUp` 完全自绘，别指望 borderlessButton 能保留自定义 label。

21. **`NSTextView.setMarkedText` 不发 `NSText.didChangeNotification`**：
    输入法组合期间（`ni'hao'ma` 还没选词上屏）想靠这个通知判断「用户已经在输入」，
    实测 fired = 0，占位文案会一直压在候选词后面。但 `textView.string` 在组合时
    立刻就有内容——所以占位显隐要盯 `string`（120ms 轮询足够），不能盯通知。
    推论：**System 控件的「想当然行为」都要写 20 行代码实测一遍**，别信文档直觉。

22. **SwiftUI `ScrollView` 就算滚动条是 overlay 也会预留宽度**：
    `scrollerStyle = .overlay`、`contentInsets = 0` 都确认过了，内容右侧仍然少 16pt，
    设置页看起来就是「左边窄、右边宽」。这不是 AppKit 占的，是 SwiftUI 布局层占的。
    要么 `showsIndicators: false`（内容宽度固定时可以），要么把这条预留算进不对称的 gutter。

## UI 验收清单（每次改界面前过一遍）

这些是踩出来的，不是理论：

1. **正在被操作的元素不能动。** 只要某个操作会写数据，就问一句：写完之后排序/筛选/高度会不会变？
   用户手里那张纸、那个面板、那行列表项，在操作结束前必须钉住。
   「最近编辑」这类按时间排序的列表，顺序只在**操作结束**（收起/关闭/失焦）后刷新。
2. **系统控件的长相必须真机看。** 离屏渲染、编译通过、SwiftUI Preview 都可能骗你：
   `Menu(.borderlessButton)` 会吞掉自定义 label、`Stepper` 的箭头小到看不见、
   `ScrollView` 悄悄预留滚动条宽度。真窗口 + `screencapture -l <windowID>` 才是证据。
3. **对齐要量化，不靠眼睛。** 左右留白差异直接量像素：`≤1px` 才算过。
   截图带窗口阴影时记得先扣掉阴影再算。
4. **输入态有四档，逐档看：** 空且未聚焦 / 空且聚焦 / 有内容 / **输入法组合中**。
   最后一档最容易漏——binding 还是空串，但用户已经在打字了。
   **而且必须真的敲字母试**：`--imetest` 用 `setMarkedText` 模拟逐个字母，
   再故意发一次无关的 `@Published`；只截一张静态图根本测不出「字母被删」。
5. **验收顺序固定：** 编译 → 断言（selftest/edgetest/imetest）→ 离屏渲染 → 真窗口截图 →
   像素测量 → 亲手走一遍用户路径。跳步就会漏。

23. **SwiftUI `TextEditor` 会在输入法组合期吞字——这是 v0.9 最严重的一次回归**（坑 21 的下半段）：
    `TextEditor` 的 `updateNSView` 里是 `if tv.string != binding { tv.string = binding }`，
    **不看 `hasMarkedText()`**。中文输入法组合时 binding 仍是空串，于是只要视图树因任何原因
    重算一次，刚敲的拼音字母就被这一行抹掉：先是占位探针每 120ms 发布 `@Published`（打字中必然发生），
    修掉它之后 `--imetest` 又测出 Toast / store 等**无关的**发布同样会吞字。
    `.equatable()` 挡不住（实测 `tv.string` 照样被写成 `""`），把占位挪到 SwiftUI 之外也只解决一半。

    根治三件事一起做：
    ① 占位改成 `EditorPlaceholderView` 用 `NSString.draw` 原生绘制，探针轮询后只改自己的 Bool、
       `needsDisplay`，**全程不发布任何 SwiftUI 状态**；
    ② **四处**输入框（主输入区 / 捕获面板 / 便签详情 / 边缘条抽出面板）的正文统一改由
       `PlainTextEditor`（自托管 `NSTextView`）渲染，只在**外层 binding 的值真的变了**
       且不在组合态时才写回；`textDidChange` 里遇到 `hasMarkedText()` 也不把拼音灌进草稿；
       抽出面板每次 `onEdit` 都写回 store，是最容易复发的一处，别漏；
    ③ ZStack 的孩子数量恒定，不给 SwiftUI 换掉 `TextEditor` 结构身份的机会。

    换掉 `TextEditor` 后 `textContainerInset` / `lineFragmentPadding` 都归零，字形起点从
    `(-1.5,-0.5)` 变成 `(0,0)`，`EditorMetrics.textOrigin` 必须跟着归零并用 `--cursortest`
    重新量像素，否则提示又会比光标偏。**结论：输入框这类控件，别让 SwiftUI 在用户打字期间
    有机会重算视图树。**

24. **`MasonryLayout` 收到 `.infinity` 宽度会 SIGTRAP**：`Int(infinity)` 直接崩，
    只判断 `width > 0` 不够。根视图没定宽（例如命令行里直接 `NSHostingView(rootView:)`）
    SwiftUI 就会给无限宽提案，`guard width.isFinite, width > 0` 才是正确兜底。

25. **列数不能只靠「最小列宽」算，图片便签会被裁**：
    v0.9.3 用 `minColumnWidth = 300` 推列数，960pt 窗口（内容区 908pt）只能出 2 列，
    卡片被拉到 ~450pt，整面墙显得又空又大。改成**以 3 列为锚点**：当前列宽 < 260pt
    才逐级减列，新增一列后每列仍 ≥ 320pt 才允许升到 4 列（`--gridtest` 覆盖 6 档宽度）。
    配套还有一个隐性回归：`NoteCard` 原来给图片「固定高度 + `aspectRatio(.fill)`」，
    列宽从 450pt 缩到 292pt 后横幅图**两端会被裁掉**（测试图右端标记整块消失）。
    改成按列宽等比缩放 `.fit` + `maxHeight: 200`，整张图完整显示。
    结论：改列数一定要拿「带横幅图的便签」截图复核，光看纯文字卡片会漏。

26. **SwiftUI 按钮在 macOS 上默认不给手型光标，而且 cursor rect 在按钮上不生效**：
    `Button` / `Menu` / `Picker` / `onTapGesture` 悬停时还是箭头，看着不像能点。
    AppKit 层这些控件是私有代理视图（实测 `KeyViewProxy`），**不是 `NSButton`**，
    所以「遍历 NSButton 设光标」的全局方案无效。

    **踩过的弯**：v0.9.5 用 `resetCursorRects` + `addCursorRect` 注册 `pointingHand`，
    单元测试只断言了「注册了 1 个 rect」，全部通过——但真机上永远是箭头。
    用真窗口探针（`CGWarpMouseCursorPosition` 移光标 + `NSApp.run()` 事件循环）复现：
    同一个垫片挂在普通 `Color` 上能变手型，挂在 `Button` 上（`background` / `overlay` 都试过）
    **一律失效**——`cursorUpdate` 只会派发给光标下那个 SwiftUI 私有视图，轮不到背景垫片。
    `.onHover` 与 `NSTrackingArea` 同样依赖事件真的派发到窗口，在自动化里也无法稳定复现。
    **教训：cursor rect / tracking area / onHover 这类「等系统来通知我」的方案，验证必须
    用真实光标位置驱动，只断言注册状态等于没测。**

    现在的做法（`Cursor.swift`）：`HandCursorRegistry` 每 40ms 读一次
    `NSEvent.mouseLocation`，逐个判断是否落在某个 `HandCursorView` 的可见矩形内。
    不依赖任何事件派发。三个关键点：
    ① 只在「进入 / 离开」的瞬间改光标，区域内每帧只做幂等 `set`（防止别的 cursor rect 改回箭头），
       否则会跟输入框的 I 形光标互相抢；
    ② 离开时按落点 `hitTest` 还原：可编辑 `NSTextView` / `NSTextField` → `.iBeam`，其余 → `.arrow`；
    ③ **不能用 `NSView.visibleRect`**：SwiftUI 托管视图里它返回的是整个窗口大小
       （实测每个垫片都报 1100×788），必须逐级与祖先 `bounds` 求交集，顺带处理滚动裁剪。
    垫片 `hitTest` 仍返回 `nil`（绝不吞点击）；**输入框绝不能加**。
    `--hovertest` 会真的移动系统光标，断言按钮/卡片变手型、输入框保持非手型、空白处恢复箭头。

27. **`TextEditor` 会把图片当文本粘**：macOS 上从访达复制一张图再 ⌘V，
    TextEditor 插进来的是一串 `/Users/.../x.png` 路径，看起来就像「不支持图片」。
    必须在自己的键盘监听里先判断剪贴板有没有图、有就吞掉这次 ⌘V。
    配套的坑：`NSPasteboard.canReadObject(forClasses: [NSImage.self])` **不认文件 URL**，
    要额外用 `readObjects(forClasses: [NSURL.self], .urlReadingFileURLsOnly)` 读一遍。

28. **偏移 / 旋转过的子视图，`convert(bounds, to: nil)` 算出来的窗口矩形不可信**（坑 26 的续集，
    也是 v0.9.7 用户拍到的那个）：边缘条四张纸签各挂一个手型垫片，只有**最上面那张**有手型，
    下面三张全是箭头。原因有两层——
    ① 每张签都带 `.offset(y: idx * 68)` + `rotationEffect`，SwiftUI 用「布局容器 + layer 位移」
       实现它们，子视图已经画到别处，容器 bounds 还停在原位；原来 `windowRect(of:)` 无脑跟
       每一层祖先求交，偏移出去的子视图当场被判成 `null`（实测 4 张签里 2 张直接算成
       `(inf, inf, 0, 0)`，第 3 张只剩半个高度）。
    ② 修法两条一起：`windowRect(of:)` **只跟真正裁剪的祖先**（`masksToBounds`，即滚动视图、
       圆角裁剪层）和窗口内容区求交；纸签这种「一整列都是可点区」的东西**整列挂一个垫片**，
       别每张签各挂一个——整列是规规矩矩的 `frame`，量得准，而且签按 `tabStep` 重叠，
       列矩形正好是各签的并集。

29. **App 在后台时，macOS 不允许任何 App 改光标**（重要，别再往这个方向修）：
    边缘条是 `nonactivatingPanel`，悬停它不会激活 App，所以用户是「在浏览器里干活，
    顺手去够屏幕边缘」——这时 `NSCursor.set()` **返回成功但屏幕上是箭头**。
    真机取证（`screencapture -C` 能连光标一起截）：前台时是手，`open -a Chrome` 把前台
    让出去之后同一个位置立刻变回箭头。三种公开做法全部无效：定时 `NSCursor.set()`、
    `resetCursorRects` + `addCursorRect`、`NSTrackingArea(.cursorUpdate)`；
    连私有的 `CGSSetConnectionProperty(..., "SetsCursorInBackground", true)` 在 macOS 15 上也
    已经失效（调用返回 0，光标不动）。**这是系统级限制，不是本项目的 bug**：后台窗口的按钮
    本来就不显示手型，全 macOS 一样。所以 `HandCursorRegistry` 不再拿 `NSApp.isActive` 当门槛
    （那是多余的自我限制），但也不要指望后台能出手型——验收必须在 App 前台时做。

30. **「手型和箭头来回闪」不是光标写得太频繁，是判定在抖**（v0.9.11，用户点纸签时拍到的）：
    原来每 40ms 判一次「鼠标点是否落在垫片上」，**这一帧没命中就立刻变箭头**。而点一下纸签
    会同时触发三件事：`makeKey()`、窗口 frame 做 0.24s 的 `animator().setFrame` 动画
    （54pt → 392pt）、SwiftUI 把 `.fan` 整棵视图树换成 `.pull`（垫片销毁重建）。
    这三件事让命中在几十毫秒里反复真假，光标被来回拨，看起来就是两个形状在打架。
    修法是把「离开」做成有状态的四条规则，而不是每帧重新决定：
    - **进入立刻**，命中第一帧就变（要跟手）；
    - **离开要动过**：自上次命中以来鼠标位移 > 6pt（v0.9.14 从 2pt 调大，过滤点击手抖），
      且连续 4 帧（160ms）未命中才回箭头。
      手没动时布局怎么变都不切——这条是治闪烁的关键；
    - **按键期间不切**（`NSEvent.pressedMouseButtons != 0`）；
    - **点击后 `hold(0.6)`**，把动画窗口期整段钉住。

    配套的三个坑，每个都能单独造成闪烁：
    - `unregister()` 里**不要立刻** `releaseHand()`：点击时旧垫片先销毁、新垫片后建，
      中间登记表是空的，马上收手就是一次肉眼可见的闪。改成 1s 后仍为空才收。
    - `isCovered()` 判定**不能带 `$0.isVisible`**：窗口 frame 动画期间这个标志会短暂为
      false，于是「我们自己正在变宽的面板」被判成「别人压在上面」——而那条分支会直接
      把光标拨回箭头。
    - 命中判定**不要只认系统报的那个 `windowNumber`**：`makeKey` 之后它会跳，改成遍历
      本 App 所有可见窗口的垫片；再加一条 sticky 记忆（上次命中的屏幕矩形，外扩 4pt），
      **只按位置**判断（v0.9.14 起不再要求「手没动」——点击时那 1~2pt 抖动会让旧条件失效）。

    验收用 `--edgeclicktest`：真实窗口、真实动画，pull 之后采 32 帧，要求 `isHand` 32/32、
    状态翻转 0 次、走「回箭头」分支 0 次。修复前同样的采样是 29/32、3 次箭头。

31. **状态机修好了，屏幕上还在闪：还有第二个「光标主人」**（v0.9.14，用户复测后拍到的）：
    第 30 条把**我们进程里的判定**修好了，但屏幕上的光标归 WindowServer 管。AppKit 的
    cursor rect 会在 `mouseMoved` / `cursorUpdate` / 窗口变 key / frame 重排时把光标设回箭头；
    我们只在 25Hz 轮询的下一帧补回来，中间 0~40ms 就是肉眼看到的一次闪。
    旧 `--edgeclicktest` 只断言 `isHand`，注释里甚至写着「不断言 `NSCursor.current`」，
    而且直接调 `pull()`、把鼠标钉死不动——**根本没测到屏幕光标，也没走真实点击事件**。

    修法是让补光标跟事件同步，不再隔着 40ms 互相拨：
    - 主 runloop 挂 `.beforeWaiting | .exit` 观察者，在**每个事件处理完**同步补一次；
      只在光标真被改掉时才 `set()`，避免每轮 runloop 都发 CGS 调用。
    - 本地/全局事件监视器再无条件兜一次（兜住「别的进程改了屏幕光标、我们进程仍记着手型」）。
    - **任何**真实鼠标按下/抬起都给宽限期（0.8s / 0.6s）。原来只有 `pull()` 有 `hold(0.6)`，
      点关闭收起、点圆钮、点面板空白这几条路径完全裸奔。
    - 宽限期内加一条粗判：指针还在边缘面板窗口 frame 里就继续算命中。抽出时窗口从
      「一条纸签」变宽成「便签 + 签列」，签列整体横移，旧命中矩形不再包含指针，
      光靠 sticky 会漏判；窗口 frame 比垫片稳定得多。

    `--clickfliptest` 手动 `NSApp.postEvent` + `sendEvent` 派发真实事件（CLI 测试二进制没跑
    `NSApp.run()`，CGEvent 合成事件不会自己派发），每帧先 `NSCursor.arrow.set()` 模拟 AppKit
    洗光标，只给 12ms（不够 25Hz 轮询补一帧）：只挂 async 事件重申时 40 帧残留 9~10 帧箭头，
    加 runloop 观察者后连跑 10 次都是 0 帧残留、0 次翻转。`--hovertest` / `--deckhovertest`
    同时验证输入框仍是 I 形、窗口空白仍是箭头，没有被「钉手型」误伤。

32. **有些仗不值得打赢：floating 面板的手型光标直接放弃**（v0.9.15，用户拍板）：
    坑 30、31 把「点击边缘便签时箭头/手型互闪」修到**测试全绿**（状态机 0 翻转、
    事件级重申 0 残留），但用户真机上仍能复现。根子是结构性矛盾：边缘面板是
    `nonactivatingPanel` + floating level，点击同时触发 makeKey、frame 动画、
    SwiftUI 整棵视图树重建，WindowServer 的光标所有权在这几百毫秒里会被系统反复
    收回——我们补得再快，也只是把闪烁压短，压不到零。

    对策不是再补一层，而是**退出这场争夺**：EdgeDeck 不再注册任何手型垫片
    （`.handCursor` 全部摘掉，`pull`/`collapse` 里的 `hold`/`recheckNextTick` 一并删），
    边缘窗口保持系统默认光标。手型机制只留给主窗口 / Sheet / 便签槽这类不做
    frame 动画的普通窗口——没有竞争源的地方它从来不闪。

    教训：**「测试全绿但用户还能复现」本身就是答案**——说明竞争发生在我们的
    可观测面之外（WindowServer），继续加补丁只是在跟系统拔河。
    `--clickfliptest` 语义随之翻转：现在断言边缘窗口**零垫片**、点击抽出全程
    手型 0 帧次，谁把 `.handCursor` 挂回 EdgeDeck 谁红。
